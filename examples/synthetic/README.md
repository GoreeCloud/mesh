# Mesh synthetic discovery fixture (nonproduction)

This is a local, dependency-free contract experiment implementing the first narrow slice of [Mesh stability gates](../../docs/stability-gates.md). It does **not** implement a network server, real MCP endpoint, webhook, connector, credentials, privacy enforcement, security product, or any cross-system control. The manifest names fictional fixture owners only. Node.js 24 or later is used for the reference harness; it is **not** a decision on Mesh's production runtime.

Run `npm test` for contract tests or `npm run demo` for an inert example. The demo prints a catalog and one expressly synthetic result. There are no installs, sockets, environment secrets, persistence, or external calls.

Contract rules:

- `mesh.capabilities.v1` declares only `synthetic-local-only` records with a bounded, unique capability ID and `status.read` operation. Manifest and capability fields are snapshotted from exact own data descriptors; hostile getters, sparse/accessor array entries, symbols, undeclared properties and throwing proxy traps are rejected without executing getter bodies. A discovered record stays `prototype` and carries **zero implicit authority**.
- Mesh policy and the simulated owning adapter must each approve an actor. All absent/throwing/false decisions are denied. The *outer* constructor options are also snapshotted from own data descriptors before access: getters, inherited/hidden fields and throwing proxies cannot execute at initialization. Adapter registration and method lookup require plain own data descriptors; getters, inherited methods and throwing proxy traps cannot trigger owner work. No write operation is supported.
- Outcomes are typed `unsupported`, `denied`, `unavailable`, `timed_out`, or `invalid_response`. Reads have a maximum one-second configurable execution budget and a 4 KiB maximum output ceiling; fixture defaults are 100 ms and 1 KiB. The base harness also limits in-flight reads to eight by default (`maxConcurrentReads`, range 1–32), refusing excess work as `unavailable` **before** invoking Mesh policy or owner callbacks; a slot is released **only when the underlying policy/owner action settles**, even if its caller has already timed out.
- Accepted result data is limited to a strictly shaped synthetic status, never arbitrary logs or user payload. No central request/payload logging exists.
- The timeout abort signal can stop cooperative fixture reads. An uncooperative promise may continue in memory after its caller times out; its admission slot deliberately remains reserved so repeated timed-out callers cannot create unbounded overlapping owner work. **An owner that never settles can exhaust all slots indefinitely and block further reads until the fixture process is reset.** That is fail-closed behavior, not reliable production cancellation. Production adapters require process/network-level hard deadlines, forcibly recoverable worker isolation, backpressure and protection against late side effects.

No part of this harness should be promoted as an operational Mesh integration until independently reviewed owner-side contracts, authorization, resilience and deployment evidence satisfy the release gates.


## Opt-in correlation evidence and concurrency admission

`evidence.mjs` adds a **nonproduction**, in-memory wrapper for the same synthetic `read()` interface. It never opens a socket, exports telemetry, performs a retry, changes the owner's response, grants a permission, or writes durable state. Opting into the wrapper creates a bounded ring of `mesh.synthetic-evidence.v1` terminal records containing **only** `schema_version`, a random local `correlation_id`, the enumerated `outcome`, and `observed_at`. No actor, request, capability name, response data, error text, credential, or raw payload is retained.

```js
import { createFixtureHarness } from './fixtures.mjs';
import { createSyntheticReadObserver } from './evidence.mjs';

const observer = createSyntheticReadObserver(createFixtureHarness(), {
  capacity: 32, maxInFlight: 8,
});
const { correlation_id, response } = await observer.read({
  actor: 'fixture.reader',
  capabilityId: 'fixture.alpha.status',
  operation: 'status.read',
});
const privateEvidence = observer.records();
observer.clear(); // explicit in-memory retention control
```

The wrapper records completion order, not invocation order. It refuses an excess concurrent read **before** calling the owner, returning the existing typed `unavailable` outcome. Calls already running are governed by the underlying synthetic harness's timeout and cancellation limits; the observer cannot stop an owner that ignores cancellation. It passes through the original result object or thrown exception, without writing either into evidence. Invalid configuration/accessors/proxies are rejected before invoking untrusted getters. Correlation IDs are local diagnostics, not signed attestations, durable audit IDs, service health proofs, authorization tokens or permission to share evidence externally.

Validation: `npm test` includes `evidence.test.mjs` alongside the existing synthetic contract tests. Live Identity, GoreeShield, Wardveil, production telemetry, durable delivery and real adapters remain unimplemented.

## Controlled synthetic owner shutdown (development only)

The fixed-code subprocess adapter now exposes an idempotent `shutdown()` method. Once invoked, the adapter denies new authorizations and reads, invalidates late resolutions of previously pending owner-policy callbacks, and signals all currently tracked child leases to terminate. Their in-flight capacity remains charged until the operating system emits each child `close` event; shutdown completion is not evidence that child processes already exited. Existing POSIX process-group cleanup also covers the fixture's deliberately attached descendants. This is useful to test application teardown and avoid orphaned synthetic operations in this one Node process.

A caller that needs explicit teardown acknowledgment may use `await owner.shutdownAndWait(timeoutMs = 2000)` (accepted integer 1–5000 ms). It marks the owner stopped, signals tracked children, and resolves `true` only after every associated OS child `close` lease has released. Several callers may await the same close sequence. A wait deadline rejects with the same generic unavailable error **without releasing live capacity or falsely claiming process termination**; a later bounded call may check again. Invalid timeout arguments throw before stopping the adapter. This API does not monitor work across separate Node processes.

This is not an automatic restart supervisor or a durable cancellation/cleanup acknowledgment API. It does not kill arbitrary code outside the trusted fixed-code worker group, enforce OS security isolation, revoke production credentials, or provide backup and recovery. No production connector or service uses this fixture.

## POSIX fixed-code process-group cleanup (development test)

When an isolated synthetic owner launches on POSIX, the fixed-code child now starts in its own process group. A deadline or caller abort sends SIGKILL to that owned group, rather than only to the immediate child, so a deliberately spawned fixed-code descendant cannot keep inherited stdout open and pin the capacity slot indefinitely. A dedicated `tree-hang` regression creates one synthetic descendant and verifies that both timeout and abort eventually reach the actual child `close` event, where the admission slot is released. Windows retains its existing immediate-child termination behavior and rejects the POSIX-only regression mode.

This improves one fixed-code, local development subprocess fixture only. It is **not a secure OS sandbox**, process-tree protection against escaped process groups, cgroup memory/CPU enforcement, arbitrary-plugin execution, a durable worker supervisor, or production recovery. The child still inherits the runner's filesystem/network privileges; production owner execution must use platform isolation, independent watchdog supervision, OS quotas, authenticated transports, audited policy and restart budgets.

## Opt-in fixed-code process cancellation fixture

[isolated-owner.mjs](isolated-owner.mjs) and its reviewed, fixed-code [child](isolated-owner-child.mjs) provide a narrow **synthetic-only** Node process-boundary experiment. It accepts no arbitrary executable, script, URL, environment variable, payload or owner plugin. Its child is spawned using the current trusted Node binary, `shell: false`, ignored stdin/stderr and a minimal environment without inherited application credentials. Output must match an exact two-field status contract and fit within 256 bytes.

The development adapter requires a caller-supplied **explicit true** local authorization callback. Even when a consumer directly calls the exported adapter rather than the Mesh harness, a read now consumes **one successful owner authorization for the same AbortSignal**; an unapproved or reused signal cannot spawn a child. Authorization additionally checks the exact six-field manifest descriptor for this fixed-code `fixture.alpha.status` owner and a valid synthetic actor identifier, then passes an **immutable, value-only snapshot** to its permit callback. A caller can mutate its original descriptor after admission without changing what a delayed policy check reads. A permit for `fixture.beta.status`, a forged descriptor, or an unrelated actor cannot acquire the alpha owner's child ticket. A newer denied/pending authorization invalidates earlier grants, including delayed policy approval that resolves out of order. Weak-keyed tickets do not persist caller identity or create an authentication system: **this is synthetic defense-in-depth, not Identity-bound authorization**. Each status read gets a separate disposable child. The caller may limit active children to 1–4 and set a 20–1000 ms hard deadline. The worker uses SIGKILL when the deadline or AbortSignal fires; an admission lease stays occupied until the child **actually closes**, not merely until the caller gives up. A per-adapter-instance monotonic launch budget additionally admits at most **16 attempted subprocess starts in a rolling 60-second window**, charging attempted spawns even if they crash immediately; excess calls fail closed before spawn. This prevents one fixture instance from starting an unbounded crash loop. **November 10 development hardening:** A second cap now reserves no more than **eight live subprocesses across all fixture instances in the same Node.js module process**, even when a caller tries to evade the per-instance cap by constructing many adapters. Every over-capacity read fails before spawning or consuming its per-instance launch budget; each admitted slot is released only on the corresponding child process `close` event. This is **not** an operating-system-wide quota, durable circuit breaker or production supervisor. Separate Node processes still have independent budgets. **November 10 additional safeguard:** a separate module-local rolling budget now permits at most **64 attempted child starts in any 60-second window across all adapter instances** in the same Node process. This prevents spawning many new fixture instances to sidestep the previous per-instance 16-start rate limit, including rapid serial crash-and-retry loops that never exceed the eight-child concurrency cap. Attempts rejected by the shared rate limit do not spawn or consume the caller's per-instance start budget. It still does not constrain any other process, provide durable restart accounting, or guarantee containment of arbitrary code. A crashed child, malformed/oversized output or late response never becomes successful status. It exposes local numeric active-child and recent-launch counts for development tests, not process IDs or logs.

The new tests exercise successful and degraded synthetic reads, default-deny callbacks, crash and oversized output, a never-resolving child, cooperative cancellation, late response attempts and hostile configuration. `npm test` runs these alongside the existing pure harness fixtures.

**Not a security sandbox:** The child still inherits the CI runner's operating-system user identity and filesystem/network privileges. It executes only the fixed repo-owned fixture, **never untrusted third-party code**. This does not provide tenant isolation, process credentials, seccomp/LSM, network deny rules, parent-death guarantees, audited privileged worker execution, cross-platform Windows/macOS behavior, durable outage handling or a safe deployable owner runtime. It does not replace the prior in-process harness, and it has no connection to a real device, VPS or Wardveil service. Issue #34 remains open for supervised production worker isolation.

## November 12, 2026 — shared admission across independent synthetic harnesses

The source-owned in-process `createSyntheticHarness` fixtures now use a shared module-level **16 in-flight operation cap** in addition to each harness's configurable lower `maxConcurrentReads` and per-actor limits. A newly constructed harness cannot bypass the module-level cap. Caller-visible timeouts **do not** release a global lease until the underlying asynchronous permit/owner action actually settles, preventing repeated noncooperative fixture work from accumulating across newly created harnesses. An isolated two-test regression saturates 16 separate harnesses, verifies the 17th is refused before owner invocation even after client timeouts, then releases the pending owners and checks recovery; denied calls do not strand slots. This bound applies only inside one Node process/module instance. It is neither persistent, tenant-scoped, multi-process, a trusted production Identity verifier nor an operating-system isolation/resource mechanism; production worker isolation remains blocked by Mesh issue #34.
